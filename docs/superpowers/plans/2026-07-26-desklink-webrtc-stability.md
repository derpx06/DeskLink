# DeskLink WebRTC Stability Implementation Plan

**Goal:** Deliver one authenticated, generation-safe WebRTC feature session for each paired DeskLink Android and desktop device on the same Wi-Fi network.

**Constraints:** Preserve application identities, keys, certificates, pairing records, ports, storage paths, DeskLink branding, and the Android WebRTC packet schema. LAN is limited to discovery, pairing, identity, and signed SDP/ICE signaling after migration.

## Delivery order

1. Establish `DeviceManager` as the sole desktop session owner, including cancellation, generation checks, bounded recovery, and clean daemon shutdown.
2. Add the desktop GStreamer WebRTC transport, signed LAN signaling, authenticated handover, and shared packet dispatcher.
3. Route regular feature packets through WebRTC and derive capability advertisements from installed handlers.
4. Replace payload sockets with resumable data-channel transfers and a safe Android-rooted phone file browser.
5. Move remote input to a persistent GNOME portal lease and complete VP8 screen tracks, beginning with phone-to-desktop rendering.
6. Add host adapters, D-Bus/CLI, accessibility-safe UI state, packaging metadata, automated fault coverage, and physical-device validation.

## Acceptance invariants

- One active session and one peer connection per device; stale readers, workers, and reconnect attempts cannot mutate newer state.
- Feature traffic is accepted only after mutual authentication, capability agreement, and bidirectional `feature-ready`.
- Pairing records and identity material are reused, never regenerated by recovery or transport replacement.
- Transfers are bounded, authenticated, resumable, checksum-verified, path-safe, and atomically published.
- Portal and MediaProjection denials are explicit states; repeated packets never cause repeated permission prompts.
- Same-Wi-Fi real-device testing is required before claiming feature completion. WSS/TURN and different-network support are deferred.
